# Data Model: In-App Problem Reports and Feedback

All schemas live in the new framework-free package `packages/feedback-engine`, written with Zod. The worker and the web app import them from there.

## FeedbackReportInput (contract v1, browser → worker)

| Field             | Type                                                                  | Rules                                                                                      |
| ----------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `schemaVersion`   | literal `1`                                                           | Required. Any other value is rejected.                                                     |
| `submissionId`    | string                                                                | Required. A UUID v4 that stays the same across retries of one draft (R5).                  |
| `kind`            | `"problem" \| "idea" \| "other"`                                      | Required (FR-002).                                                                         |
| `description`     | string                                                                | Required. 1–4,000 characters after trimming, counted in code points (FR-014).              |
| `contactEmail`    | string, optional                                                      | Absent or empty means no contact. At most 254 characters and a valid email shape (FR-004). |
| `meta.appVersion` | string                                                                | Matches `^\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$` and is at most 32 characters.                   |
| `meta.area`       | `FeedbackArea`                                                        | One of `FEEDBACK_AREAS` (R8).                                                              |
| `meta.browser`    | `"chrome" \| "edge" \| "firefox" \| "safari" \| "samsung" \| "other"` | R9.                                                                                        |
| `meta.screen`     | `"narrow" \| "wide"`                                                  | R9.                                                                                        |
| `website`         | string, optional                                                      | Honeypot. It must be absent or empty (R6).                                                 |

The object is **strict**: unknown keys at any level are rejected (FR-014). The worker bounds the raw body at 16 KB before parsing.

## FeedbackReportRecord (what the maintainer receives)

This is built by the worker from a valid input. It is never stored by the worker; it exists only to render the GitHub issue.

| Field          | Source                                                                   |
| -------------- | ------------------------------------------------------------------------ |
| `reference`    | Generated by the worker (R7), for example `CC-7F3K-9Q2M`.                |
| `kind`         | From the input.                                                          |
| `receivedAt`   | Worker clock, ISO 8601 UTC.                                              |
| `description`  | From the input, after `normaliseText` and then `redactSecrets` (R2, R3). |
| `contactEmail` | From the input, trimmed, or absent.                                      |
| `meta`         | The four allowlisted values from the input.                              |

It is rendered by `renderTriageIssue(record)` as `{ title, body, labels }` (R2).

## FeedbackReceipt (worker → browser, success)

`{ "reference": "CC-7F3K-9Q2M" }`, returned with HTTP 201, or HTTP 200 for a repeated delivered submission. It never includes the issue number, URL, repository or any storage detail (FR-018).

## FeedbackError (worker → browser, failure)

`{ "error": { "code": FeedbackErrorCode, "message": string } }`

| Code               | HTTP | Meaning                                                                             | Form message (FR-009)                             |
| ------------------ | ---- | ----------------------------------------------------------------------------------- | ------------------------------------------------- |
| `invalid`          | 400  | Contract violation, honeypot filled, or body too large (413 is mapped to this code) | "Please check the form" plus the field-level hint |
| `forbidden_origin` | 403  | Origin missing or not allowed                                                       | Unavailable message                               |
| `rate_limited`     | 429  | Burst, hourly or daily cap reached; carries `Retry-After`                           | Limit message                                     |
| `in_progress`      | 409  | The same submission is being delivered                                              | Retried silently (R12)                            |
| `unavailable`      | 503  | GitHub refused or did not respond                                                   | Unavailable message                               |
| `misconfigured`    | 503  | Token, repository or hash key missing                                               | Unavailable message                               |

The messages are fixed strings and never include upstream error text.

## SubmissionMarker (worker R2, no report content)

Key: `feedback/submission/<hmac(submissionId)>`

`{ "state": "pending", "at": <epoch ms> }` → `{ "state": "delivered", "reference": "CC-…" }`

Transitions:

- absent → `pending`, claimed with `etagDoesNotMatch: "*"`.
- `pending` → `delivered` when GitHub succeeds.
- `pending` → deleted when GitHub definitively refuses the report, or when the request is refused before delivery (quota refusal, 429).
- `pending` → kept, with its quota slots, when the outcome is unknown: a timeout or dropped connection. The marker then guards retries until it goes stale after 2 minutes (see R5).
- A `pending` marker more than 2 minutes old → re-claimed by etag compare-and-set.

All markers are removed by the 2-day lifecycle rule on `feedback/`.

## QuotaCounter (worker R2)

Keys:

- `feedback/quota/hour/<yyyyMMddHH>/<sourceHash>` with `{ count }`, at most 5.
- `feedback/quota/day/<yyyyMMdd>/<sourceHash>` with `{ count }`, at most 20.

Counters are incremented by compare-and-set, released by a compare-and-set decrement when delivery fails, and expire through the lifecycle rule. `sourceHash` is the first 16 bytes of `HMAC-SHA-256(FEEDBACK_HASH_KEY, CF-Connecting-IP)`, as hex.

## FeedbackDraft (browser memory only)

`{ submissionId, kind, description, contactEmail, status: "editing" | "sending" | "sent" | "failed", reference?, failure?: "offline" | "limited" | "unavailable" | "invalid", retryAfterSeconds? }`

The draft is held in the `feedbackDialog` store for the page's lifetime, never persisted, and replaced with a fresh `submissionId` after a success or when the user chooses "Send another".

## FeedbackMetric (log line)

`{ "event": "feedback.report", "outcome": "accepted" | "duplicate" | "rejected" | "limited" | "unavailable" | "misconfigured", "kind"?: FeedbackKind }`

Any other field or value means the line is not emitted (R11).
